# Bitez Android release guide

Prepared 4 October 2026. A signed App Bundle is a build artifact, not confirmation of Play approval or completion of device QA.

## Files and first upload

- `bitez-1.0.0-play.aab`: signed bundle for Play Console; cannot be installed directly.
- `bitez-1.0.0-test.apk`: signed release APK for direct Android phone testing.
- `bitez-android-launch-assets.zip`: store icon, feature graphic, listing draft, this guide, build verification and checksums.
- `bitez-private-upload-key-backup.zip`: private upload key, password, certificate and rebuilding instructions. Keep two secure backups. Never put this file in the public repository or send it to testers.

1. Merge the wrapper pull request and wait for Vercel to deploy the web back-navigation handler. Verify https://bitez-sg.vercel.app/ works.
2. Create/verify your [Google Play developer account](https://play.google.com/console/signup). Google documents a **US$25 one-time registration fee**; bank conversion/taxes may vary. New personal accounts also require identity and Android-device verification. Publishing this wrapper does not itself require a paid wrapper subscription. Hosting, database, production email and later traffic are separate costs.
3. Create app: **Bitez**, English, App, Free. Choose Singapore as the initial country. Application ID is `com.padmakarpimpale.bitez`; confirm it before first upload because it cannot be changed for this app listing later.
4. Enable Google Play App Signing using Google's generated app-signing key. Upload the signed AAB to **Internal testing** first. Resolve any Play pre-launch errors before inviting a broader test group. Do not upload the unsigned bundle generated by repository CI.
5. Complete store listing and App content: privacy policy, app access, ads, content rating, target audience, Data safety and account deletion. Attach real Android screenshots. Draft assets do not include invented Android screenshots.
6. For personal developer accounts created after 13 November 2023, run **closed testing with at least 12 testers opted in continuously for 14 days**, then apply for production access. Internal testing alone does not meet that requirement. Respond to feedback and keep evidence of testing; the elapsed period does not guarantee approval.
7. After approval and passing the launch checks below, submit production release. Keep staged rollout and crash/pre-launch monitoring available.

Sources: [account setup and fee](https://support.google.com/googleplay/android-developer/answer/6112435), [new personal account testing](https://support.google.com/googleplay/android-developer/answer/14151465), [App Signing](https://developer.android.com/studio/publish/app-signing), [target API policy](https://support.google.com/googleplay/android-developer/answer/11926878).

## Launch checks to complete on actual Android phones

The automated build verifies compilation, URL trust policy, lint and release signatures. It does not prove the following flows work on phones. Use at least two accounts on separate devices, including an older supported Android and a current Android:

| Flow | Pass condition |
| --- | --- |
| First launch | Icon/splash render, agreement is readable with large fonts, decline exits, legal links work, acceptance persists after restart. |
| Signup and recovery | Production SMTP delivers verification/reset emails to external addresses reliably. Browser email flow and subsequent in-app sign-in work. Wrong credentials do not create a session. |
| Session | Restart/background/resume preserve login, logout clears access, account deletion removes access. |
| Location | Approximate and precise location work only after user action. Denial remains usable with area selection. Android settings revocation and repeated prompts do not crash. |
| Host/join | Host a genuine test run at a public pickup point. Second user finds/joins it, adds items, cancels and rejoins. Duplicate taps do not create duplicate orders. Host counts in the fee split. |
| Chat | Only active members can read/post. Two devices exchange realtime messages. Leaving/removal stops access. Block/report controls work and the operator can process reports. |
| Lifecycle | Lock/order/cancel/complete transitions, unfinished orders, cutoff times and delivery share changes remain correct. |
| Navigation | Android back closes run/chat dialogs first, returns from Host/My runs/Account/Legal to Discover, then exits. Keyboard does not cover chat send or bottom actions. |
| Sharing | Run invitation opens the Android chooser and contains only its public run URL. Browser/Android invite flow reaches the intended run after login. |
| Connectivity | Offline launch shows retry. Lost connection does not falsely confirm joining/sending. Restore connection/retry, SSL failures and background/resume recover safely. Chat has no background push alerts in this version. |
| Layout/accessibility | Portrait/landscape, display cutouts, Android edge-to-edge, keyboard, large text and screen reader labels are usable. |
| Deletion/moderation | Account deletion and public deletion-assistance URL are reachable. Reporter can flag UGC/users; blocking hides/intercepts the intended content/participation. Establish report-review ownership and response process before public launch. |

Before wider launch, confirm production Auth/SMTP, abuse/rate limits, database backups and an operator process for reports. Run Google's pre-launch report after upload. No signed-in physical-device test has been performed by the build process itself. Do not describe the app as fully production tested until these checks are recorded.

## Store listing draft

**App name:** Bitez

**Short description:** Join nearby food runs, coordinate in group chat and share the delivery fee.

**Full description:**

Bitez brings Singapore neighbours together for a shared food run.

Find a nearby run by restaurant or pickup area, or host one yourself. Join the group, choose your food before the cutoff and coordinate with the host in the run chat. Collect from one public pickup point and share the delivery fee with the people taking part.

With Bitez you can:
- Search nearby food runs and choose an area manually or use optional location access.
- Host a run with a restaurant, cutoff time, delivery fee and public pickup point.
- Join a run, save your food choices and see your estimated delivery share.
- Talk with the host and other active participants in the run's group chat.
- Share a run invitation and manage your reservations from My runs.
- Choose an optional invitation to eat together when the host offers it.

Bitez is a community pilot. Hosts arrange restaurant orders, collection and final costs directly. Bitez does not collect payments, deliver food or guarantee restaurant orders. Delivery shares depend on the total fee and active participants; food costs are separate. Meet at a safe public pickup point and confirm allergens with the restaurant.

**Category suggestion:** Food & Drink. **Ads:** No, for this build. **Support:** 2002padmakar@gmail.com. **Website:** https://bitez-sg.vercel.app/. **Privacy and deletion assistance:** https://bitez-sg.vercel.app/privacy. Confirm the operator email is monitored before publishing.

Provide at least two real phone screenshots after completing QA (Discover and run chat/host flow are useful). Capture test accounts and public test pickup details without private information. The generated feature graphic describes the current function; it is not a screenshot. Do not claim payment integration, delivery guarantees or background notifications.

## App content / Data safety worksheet

Review actual collection and provider logging before submitting; this is a worksheet, not a completed declaration. A hosted WebView still transmits data and does not justify answering "no data collected".

| Data type to assess | Actual use |
| --- | --- |
| Personal info: email, name, user ID, address | Supabase account email/ID; display name; profile postal code and optional block. Account/profile records persist. Profile is required to host/join; display name and public pickup details are visible as described by the privacy policy. |
| Precise and approximate location | Foreground optional device location for discovery/pickup, transmitted in search requests; public pickup coordinates stored when hosting. Area selection is available. Check provider logs and Google's ephemeral-processing definitions before answering retention fields. |
| Messages: other in-app messages | Member group chats, announcements and reports persist on Supabase until relevant deletion. The 30-day chat window limits access, not database retention. Messages are visible to active members. |
| App activity / other user-generated content | Hosted food runs, selected food items, reservations, reports and blocked-neighbour list. Assess purchase-history classification even though no payment is collected. |
| Diagnostics and identifiers | Inspect Vercel/Supabase operational logging and any later analytics/crash SDK. This wrapper adds no ads, analytics or native crash SDK. Do not infer that providers collect nothing. |

Purpose is app functionality, account management and safety/moderation. Data travels over HTTPS. Account deletion is available inside Account and via the public privacy/deletion assistance page. Evaluate disclosure of member-visible messages/run details and provider service-processing exceptions using Google's definition of "sharing". No payment-card, contacts, camera or microphone collection is implemented. Do not claim independent security review or end-to-end encryption. Complete the content-rating questionnaire honestly for member chat; do not mark the app child-directed without assessing the necessary safeguards.

For **App access**, give Google a dedicated, working reviewer account with verified email and a usable test run/second account if required. Supply credentials privately in Play Console, never in this repository. Remove expiry/OTP barriers that would prevent review without weakening production authorization. Do not use the owner's personal login.

Sources: [Data safety](https://support.google.com/googleplay/android-developer/answer/10787469), [account deletion](https://support.google.com/googleplay/android-developer/answer/13327111), [user-generated content](https://support.google.com/googleplay/android-developer/answer/9876937), [preview assets](https://support.google.com/googleplay/android-developer/answer/9866151).

## Updates and signing backup

Keep the upload keystore, password and alias privately. Losing an upload key requires Play's upload-key reset process; never silently create a replacement for the same release. Android Studio can open the `android/` folder. For later uploads, increment `versionCode`, rebuild with the same upload key and review any permission/privacy changes. Web changes still need regression testing because the wrapper loads the live production site.

Verified automatic App Links can be added after Play supplies the app-signing certificate. Use that fingerprint in the website's `/.well-known/assetlinks.json`, not the private upload key certificate. The first wrapper intentionally makes no false verification claim.
